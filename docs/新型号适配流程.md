# 新型号适配流程

给维护者：把一个新型号从"未知设备"变成"档案支持"的步骤。

## 前提

适配新型号**必须有一台真机**。没有真机、没有抓包，只能靠猜——不可靠。所以核心机制是：让有设备的用户用采集器 App 导出日志，维护者离线逆向。

## 架构基础

型号相关常量已全部收敛到设备档案：

```
assets/profiles/c1.json     ← C1 的档案（UUID / 命令号 / 回包步长 / CELT 参数）
```

由 `DeviceProfile.java` 读取，对外提供 getter。`Proto` / `PenLink` / `WavFile` 通过 `DeviceProfile.get()` 取值，不再散落硬编码。

加新型号的目标形态：**新增一份 `assets/profiles/xxx.json`，不改 Java 代码**（自动识别逻辑在后续步骤接入）。

## 适配步骤

### 1. 拿到日志

用户用独立的采集器 App（开发中）连接设备，按固定顺序点探测按钮，导出带时间戳的协议日志：

- 设备名、SN、GATT 服务与特征 UUID 清单
- 每条发出的命令 hex + 时间戳
- 每个回包 hex + 时间戳
- `B001` 数据通道的原始帧样本

### 2. 对照 C1 档案逆向

把日志和 `c1.json` 逐项对照：

| 档案字段 | 从日志哪里找 |
|---|---|
| `uuids.*` | GATT 服务/特征清单 |
| `commands.*` | 探测按钮发出的命令与回包的对应关系 |
| `responses.*` | 设备主动推来的命令号 |
| `parse.sessionStrides` | 会话回包的结构（试 12/8/4 字节步长） |
| `parse.fileStep` | 文件回包步进 |
| `audio.celtMode` | 音频帧样本，试不同 CELT mode 解出正常 PCM |
| `capacitiesTag` | 能力协商回包里的 ASCII 标识 |

### 3. 做一份新档案

复制 `c1.json` 改成 `xxx.json`，填入逆向出的值。字段含义见文件内注释和 `DeviceProfile.java`。

### 4. 验证

用真机跑全流程：

- 扫描连接、电量、列表
- 下载并解码出音频（能出声是关键门槛）
- 转写、现场录音、隐蔽、空间

任何一项不对，回到第 2 步修正档案。

### 5. 合并与发布

- 档案文件提交到 `assets/profiles/`。
- 更新 [设备支持表](设备支持表.md)，标注验证者和已验证功能。
- 发新 Release，更新 App 内的型号识别逻辑（后续步骤）。

## 音频解码兜底

CELT 的 mode / 采样率最容易猜错。档案里保留 `celtMode` 和 `celtModeFallback` 两个候选：加载时先试主 mode，失败自动回退到备选 mode。这只解决"mode 猜错"的情况；若编码方案完全不同，需要引入新的解码库。
